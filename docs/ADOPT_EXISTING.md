# 既有網站導入 SOP｜不破壞既有專案

> **不要為了套用這個範本，就直接覆寫已經運作的網站。**

## 建議步驟

1. 先記錄現有 GitHub 正式分支、最新穩定 Commit、版本號及部署方式。
2. 建立完整的原始碼備份與正式部署 ZIP；若有資料庫，另外執行符合現有方案的備份。
3. 在測試分支逐步引入 `docs/`、`templates/`、`CLAUDE.md`、`.github` 中**適合現有技術棧**的部分。
4. 由 Claude 檢視現有專案的 build／test 命令與 GitHub Pages 部署方式，再調整本範本的 Actions。
5. **不要直接用本範本的 `site/`、`package.json`、`scripts/build.mjs` 覆寫既有網站**，除非你真的要把專案改成此靜態架構。
6. 先在獨立分支／測試環境通過原有功能的回歸測試，才能考慮合併。
7. 既有 Supabase 專案須先列出所有正式資料表、RLS、Realtime 與遷移歷史，避免將範本當成重置腳本。

## 原則

- 舊專案先**導入流程及文件**，必要時才逐步導入工具。
- 若舊版號不同，不用強制立即改成 `v1.0.0`。
- 若正式環境使用既有 Actions，先保留；本範本 `pages.yml` 是合併 main 後**自動部署**，請先在新環境驗證再取代舊部署流程，避免兩套 Actions 同時發布。
- 對外宣稱完成之前，仍須由你確認實機驗收。

> 本範本（V1.2，發布流程沿用 V1.1）的 `release.yml` 需要現有專案採用對應 `scripts/package_release.py` 與 `dist/` 結構；導入既有網站時，先請 Claude 依照目前技術棧調整建置與打包。
