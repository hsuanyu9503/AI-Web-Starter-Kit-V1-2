# ChatGPT × Claude 交叉 Code Review SOP｜V1.2

## 一、權責和邊界

- **Claude Code（作者）**：實作、單元／回歸測試、提交 PR、匯出固定版本差異、逐條回應審查問題；修復後重新執行測試。
- **ChatGPT（第二視角）**：在可取得 PR 真實程式差異／原始檔案時，獨立對照 SPEC／DESIGN／TECH，指出具體風險；不能從摘要或截圖假裝看過完整程式庫。
- **你（負責人）**：確定風險級別、範圍與取捨；批准或駁回合併與 Release。ChatGPT 不能直接代表你點擊 GitHub 的 Approve／Merge。
- **GitHub**：`validate` 自動狀態檢查與分支保護；它**不會自行強制**確認 ChatGPT 曾經審查，除非日後另行實作受信任的審查機制。

## 二、開始 Code Review 前（固定版本）

1. Claude 先在 PR 說明列出基準 SHA、HEAD SHA、修改檔案、測試命令與結果、已知風險。
2. 依 `docs/RISK_POLICY.md` 標記 L1／L2／L3 和理由。
3. ChatGPT 可透過已授權的 GitHub 讀取權限、實際程式檔或經檢查的差異包取得源碼；若只有摘要，僅可進行需求審查。
4. 若使用 `scripts/export_review_packet.py`，在 Claude 的**開發分支**執行並核對輸出中沒有私人資料，再分享差異文件。預設寫入 `.review-packets/`，不提交 Git。
5. 大型改動需包含受影響模組的完整關鍵檔案，不可只憑差異片段推斷全部呼叫鏈；若證據不足，要求補件。

## 三、審查流程

1. **規格一致性**：功能是否符合 SPEC／DESIGN？是否擅自修改原本限制？
2. **回歸／資料**：狀態、例外情況、錯誤處理、資料流、權限與同步是否有影響？
3. **程式品質**：是否存在不必要重構、重複邏輯、未測試支線、破壞相容性？
4. **證據核對**：CI 是否對應同一個 Head SHA？哪些測試只有作者宣稱、哪些真的有輸出？
5. **審查輸出**：使用 `templates/CHATGPT_CODE_REVIEW.md` 每項給一個 `REV-001` 編號、嚴重程度、檔案位置、證據、重現步驟與建議。
6. **Claude 修正**：根據 `templates/REVIEW_FIX_HANDOFF.md` 實作，使用 `templates/CLAUDE_REVIEW_RESPONSE.md` 逐項說明已修／不適用／需決策；對不合理建議可附證據提出異議。
7. **複驗**：ChatGPT 檢查修正後最新 Head SHA 的相關差異；Claude 重跑受影響測試；使用者確認是否允許合併。

## 四、各等級最低交付

| 等級 | 最低證據 | ChatGPT 責任 | 使用者責任 |
|---|---|---|---|
| L1 | PR 差異／必要截圖／CI 結果 | 確認修改侷限、需求符合；可用短版紀錄 | 實際確認畫面或文字並同意合併 |
| L2 | 固定 SHA、差異、相關完整檔案、測試與操作證據 | 完成書面差異審查，列出未驗證處 | 確認重大問題已處理再合併 |
| L3 | L2 + 測試／正式環境分離、備份與復原證據、專項安全檢查 | 全面風險檢查；不能單憑 AI 審查代替必要資安或專業查核 | 明確核准正式資料／部署操作，必要時另找專業審查 |

## 五、驗收凍結

- 審查紀錄中標註 `Reviewed Head SHA`。如果 PR 追加 Commit，至少重新比對新差異與失效的測試證據；L2／L3 須更新審查紀錄。
- 只接受符合指定版本、`validate` 成功、無未解除阻擋項目，且**你**確認的 PR。
- 單人 Repo 不要為了「AI 審查」而強制設定必須由第二個 GitHub 帳號 Approve；GitHub 的正式審查核准與 ChatGPT 的報告不同。
- Review 與 Issue 檔案不可包含 API keys、個資、正式資料或未授權公開的程式碼。
- 結果寫入 `docs/REVIEW_LOG.md`（可簡要）與 PR 討論區；核准結論仍由你做出。
