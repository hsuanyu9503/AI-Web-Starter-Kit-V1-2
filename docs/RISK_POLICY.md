# PR 變更風險分級｜V1.2

## 目的與決策者

每個 PR 在開發前和審查前必須標示風險等級；**不得因變更行數少就判斷低風險**。Claude 提出初評與理由；ChatGPT 可質疑並提出升級；**由專案負責人決定最終等級與驗收深度**。無法判斷時先當高一級處理。

| 等級 | 常見範例 | 審查方式 | 合併門檻 |
|---|---|---|---|
| L1 低風險 | 文案、純視覺微調、非行為性的文件更新 | Claude 自測 + ChatGPT 針對 PR 範圍及需求比對（可簡化書面紀錄） | `validate` 成功、必要畫面／連結驗收、使用者核准 |
| L2 中風險 | 新互動、狀態邏輯、API 串接、較多檔案的功能修改 | ChatGPT 檢查**實際程式差異**、回歸影響與測試證據，形成審查紀錄 | 所有 BLOCKER/HIGH 解除，重要 MED 修復或由使用者明確承擔，CI 與功能驗收成功 |
| L3 高風險 | 登入權限／RLS／資料庫遷移、正式資料、資安、同步競態、破壞相容性、依賴升級或全面重構 | ChatGPT 獨立深度審查 + Claude 回覆逐條修正 + 專項安全／整合／復原測試 | 未解決 BLOCKER/HIGH 不准合併；使用者在證據完整後明確核准，正式資料操作需另外授權 |

**強制升級 L3：** 只要涉及正式資料、秘密金鑰、存取權限、支付、部署權限、刪除／破壞性操作、回復機制、跨使用者資料可見性，即使只改一行也視為 L3。

## 改動後重新判級

- Claude 新增 Commit、更改依賴或擴大修改範圍時，需更新風險等級；重要變更需重新審查。
- 審查對象必須固定：`Repository`、`PR URL`、`Base SHA`、`Head SHA`。不同 Head SHA 的審查不可直接沿用。
- ChatGPT 審查證據分三類：`已核對實際程式碼`、`僅取得差異／測試報告`、`只有截圖／口頭摘要`。後兩者必須標示限制；第三類不可宣稱完成 Code Review。
- GitHub CI `validate` 是技術門檻，不等於人類／ChatGPT 已審查，也不能替代實機驗收。
- 如果風險不明、缺少原始碼或缺少必要測試證據，標記**未驗證**，不可填「通過」。

## 發現問題的決策規則

- **BLOCKER**：資料損毀、未授權存取、機密洩漏、不可回復的正式環境變更等；未解決前不合併。
- **HIGH**：主要功能失效、顯著回歸、未處理的高風險競態／權限漏洞；未解決前不合併。
- **MEDIUM**：次要流程或可用性問題；須修復，或記錄由使用者明確接受的限制與處理計畫。L3 專案不得草率豁免。
- **LOW / NOTE**：小瑕疵、風格建議；可列後續 Issue，但仍需記錄。
